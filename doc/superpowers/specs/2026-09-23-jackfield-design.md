# Jackfield: дизайн надёжного кроссплатформенного Flutter-плагина звонков

Дата: 2026-09-23

## 1. Назначение

Jackfield — Flutter-плагин для управления системным представлением и локальным жизненным циклом входящих и исходящих звонков на Android, iOS, macOS, Windows, Linux и Web.

Главный приоритет проекта — надёжность. Второй приоритет — человечный и предсказуемый публичный API. Универсальность допустима только там, где она не скрывает реальные различия платформ и не ухудшает стабильность.

Jackfield не передаёт аудио или видео и не реализует бизнес-сигналинг. Приложение самостоятельно подключает WebRTC, LiveKit или другой медиатранспорт и управляет серверной сессией звонка.

## 2. Область ответственности

Jackfield отвечает за:

- системный UI и уведомления звонка;
- локальный автомат состояний входящего и исходящего звонка;
- действия пользователя: ответ, отклонение, завершение, mute и hold;
- координацию доступной системной аудиосессии;
- надёжное сохранение, повторную доставку и подтверждение событий;
- опциональную HTTPS-доставку событий без работающего Flutter;
- нативные точки входа для push-приглашений и управление push-токенами;
- обнаружение реальных возможностей текущей платформы;
- диагностику очередей, разрешений и платформенных ошибок.

Приложение отвечает за:

- авторизацию пользователя;
- серверное состояние и бизнес-правила звонка;
- формат и отправку серверных push-сообщений;
- медиатранспорт, комнаты, аудио- и видеопотоки;
- подтверждение успешного или неуспешного выполнения запрошенного системного действия.

## 3. Структура репозитория

Проект является одним Flutter-пакетом и использует идентификатор `dev.albizia.jackfield` для платформенного scaffolding.

```text
jackfield/
├── lib/                     # публичный Dart API и Dart-координатор
├── android/                 # Android-адаптер
├── ios/                     # iOS-адаптер
├── macos/                   # macOS-адаптер
├── windows/                 # Windows-адаптер
├── linux/                   # Linux-адаптер
├── web/                     # web assets при необходимости
├── example/                 # Flutter-приложение для всех платформ
├── server_example/          # изолированный пример интеграции на Go
├── docs/                    # архитектура и руководства
└── .github/workflows/       # GitHub Actions
```

Платформенные адаптеры находятся в одном пакете и следуют общему типизированному контракту. При росте проекта их можно федерализовать без изменения публичного API.

`server_example` не является частью библиотеки, не подключается как зависимость, не влияет на её runtime, сборку или публичный API. Это эталон интеграции и один из ручных тестовых стендов.

## 4. Архитектурные слои

### 4.1. Публичный Dart API

Предоставляет типизированные команды, события, конфигурацию и capability matrix. Пользовательский контракт не использует неструктурированные `Map<String, dynamic>`.

### 4.2. Dart-координатор

Проверяет допустимость переходов, дедлайны, последовательность и идентификаторы. Он разделяет запрос действия, фактическое выполнение бизнес-операции и подтверждение обработки события.

### 4.3. Платформенные адаптеры

Каждый адаптер реализует доступные системные механизмы и честно сообщает ограничения:

- iOS: CallKit и PushKit;
- Android: Telecom/Core-Telecom с notification fallback;
- macOS: системные уведомления и доступная координация аудиосессии;
- Windows: системные уведомления, действия и доступные call API;
- Linux: desktop notifications/DBus и runtime capability detection;
- Web: Notifications API, Service Worker, Push API и IndexedDB.

Недоступная операция возвращает `unsupported`, а не имитирует успех.

### 4.4. Надёжная доставка

Каждый адаптер реализует долговечные inbox и outbox с моделью `persist → publish → acknowledge`. Событие фиксируется до публикации. Flutter-доставка и HTTPS-доставка подтверждаются независимо.

## 5. Модель данных

Идентификаторы имеют разные типы и назначение:

- `CallId` идентифицирует одну попытку звонка;
- `ActionId` идентифицирует конкретное действие пользователя или ОС;
- `EventId` идентифицирует запись доставки и используется для дедупликации;
- `sequence` — монотонный номер события внутри `CallId`.

Основные значения также представлены отдельными типами: `Caller`, `CallMedia`, `EndReason`, `ActionResult`, `JackfieldCapabilities` и `JackfieldFailure`.

Версионированный wire-format одинаково интерпретируется Dart и нативными адаптерами. Миграция локального формата выполняется вперёд совместимым образом и проверяется общими fixtures.

## 6. Автомат состояний

Основной путь:

```text
created → ringing → connecting → active → ending → ended
                    ↘ failed
```

Переходы выполняются идемпотентно. Повторное завершение возвращает известный итог вместо создания нового перехода. Невозможный переход возвращает типизированную ошибку `invalidState`.

Сервер остаётся источником бизнес-истины, Jackfield — источником локального системного состояния. Серверное завершение закрывает локальное представление звонка даже при ошибке записи нового события; вызывающая сторона получает диагностируемый частичный отказ и может выполнить reconciliation.

## 7. Поток действий и событий

Пример ответа на звонок:

1. Пользователь нажимает «Ответить» в системном UI.
2. Jackfield сохраняет `AnswerRequested` с `actionId`, `eventId`, `callId`, `sequence` и deadline.
3. Событие публикуется во Flutter и, если включено, помещается в HTTPS outbox.
4. Приложение подключает сигналинг и медиа.
5. Приложение вызывает `completeAction(actionId, result: ...)`.
6. При успехе Jackfield переводит звонок в `active`; при отказе корректно завершает действие и звонок.
7. Приложение отдельно вызывает `acknowledgeEvents(eventIds)` после сохранения или обработки событий.

Повторная доставка является штатным поведением. Получатель дедуплицирует события по `eventId` и учитывает `sequence`. Подтверждение выполнения действия и подтверждение получения события никогда не объединяются.

## 8. Публичный API

Основной фасад — `Jackfield.instance`. Первая стабильная линия API включает:

- `initialize(JackfieldConfiguration)`;
- `capabilities()`;
- `reportIncomingCall(IncomingCall)`;
- `startOutgoingCall(OutgoingCall)`;
- `updateCall(CallUpdate)`;
- `endCall(CallId, EndReason)`;
- `completeAction(ActionId, ActionResult)`;
- `acknowledgeEvents(Iterable<EventId>)`;
- `events` с replay неподтверждённых событий;
- `diagnostics()` для состояния разрешений, inbox/outbox и последней ошибки;
- управление push-токенами и platform entrypoints без привязки к провайдеру.

Безопасные значения используются по умолчанию, но библиотека не запрашивает системные разрешения скрытно. Ожидаемые отказы возвращаются как структурированные результаты. Неожиданные программные ошибки могут завершаться исключением.

Платформенные escape hatches допускаются только для возможностей, которые нельзя корректно выразить общим контрактом. Они изолируются в платформенных конфигурациях и не изменяют базовую семантику.

SemVer применяется к Dart API и wire-format. Устаревание сопровождается документированным периодом миграции.

## 9. Capability matrix

`capabilities()` сообщает не только наличие функции, но и активный механизм, ограничения и уровень гарантии. Минимальные категории:

- системное представление входящего звонка;
- исходящий звонок;
- answer/reject/end;
- mute/hold;
- фоновый native entrypoint;
- долговечный inbox/outbox;
- автономные HTTPS callbacks;
- push token management;
- точность deadline;
- ограничения force-stop, DND и lock screen.

Документация содержит версионируемую таблицу заявленных возможностей и отдельно — матрицу фактически проверенных устройств и провайдеров.

## 10. HTTPS callbacks

Callbacks опциональны и работают независимо от Flutter там, где платформа допускает фоновое выполнение.

Контракт включает:

- версионированный JSON envelope;
- `Idempotency-Key: eventId`;
- HTTPS по умолчанию;
- ограниченный exponential backoff с jitter;
- поддержку `Retry-After`;
- отдельные политики для `4xx`, `401/403`, `429` и `5xx`;
- TTL и ограничение размера очереди;
- остановку очереди при ошибке авторизации до ротации credentials;
- порядок внутри одного `callId` без блокирования независимых звонков.

Успешный HTTP callback не подтверждает Flutter-событие. Секреты хранятся в защищённом системном хранилище, если оно доступно. Callback payload не содержит media credentials и минимизирует персональные данные.

## 11. Push-интеграция

Jackfield предоставляет provider-agnostic нативные точки входа и управление push-токенами. Приложение и его сервер определяют транспорт, авторизацию и бизнес-формат приглашения.

Адаптеры поддерживают получение приглашения до запуска Flutter в пределах возможностей ОС. Библиотека не навязывает Firebase приложению и не включает Firebase SDK в общий Dart API.

## 12. Типизированные ошибки и диагностика

Основные категории ошибок:

- `unsupported`;
- `permissionDenied`;
- `invalidState`;
- `deadlineExceeded`;
- `storageFull`;
- `authenticationRequired`;
- `temporarilyUnavailable`;
- `platformFailure`.

Нативные коды и безопасные диагностические подробности сохраняются как дополнительные данные, но приложение не обязано разбирать строки. Диагностика показывает последнюю ошибку, размеры очередей, состояние фоновой доставки и активный платформенный механизм.

Jackfield явно документирует ограничения ОС и браузеров. Он не гарантирует фоновый запуск после force-stop, точные таймеры, сохранение Service Worker или обход DND.

## 13. Изолированный Go server example

`server_example` демонстрирует один интеграционный сценарий и используется как ручной стенд. Он не является обязательным backend и не влияет на библиотеку.

Пример:

- отправляет FCM data message через Firebase Admin SDK for Go;
- формирует Jackfield envelope с `callId`, TTL и минимальными данными вызывающего;
- хранит минимальное тестовое состояние звонка;
- принимает идемпотентные HTTPS callbacks;
- демонстрирует accept, reject, end и серверное завершение;
- проверяет bearer credentials или подпись callback;
- получает Firebase service-account credentials только из окружения;
- содержит Dockerfile и инструкции локального запуска;
- явно перечисляет меры, необходимые для production.

Автоматические тесты Go-примера проверяют его собственную логику. Реальная отправка FCM запускается вручную с предоставленными оператором credentials и считается отдельным provider/device evidence, а не обязательным CI gate библиотеки.

## 15. Проверка

### 15.1. Автоматические уровни

- Dart: модели, автомат состояний, сериализация, идемпотентность и API.
- Contract fixtures: общий wire-format для Dart и нативных реализаций.
- Android: unit/Robolectric и сборка example.
- iOS/macOS: Swift-тесты и сборка example.
- Windows/Linux: нативные тесты и сборка example.
- Web: Service Worker, IndexedDB, Push, Flutter JS и Wasm smoke.
- HTTP: retry, deduplication, `Retry-After`, offline/restart, token rotation, overflow и recovery.
- Go: format, vet, test и build без Firebase credentials.

### 15.2. Сквозные сценарии

Проверяются входящий и исходящий звонок, answer/reject/end, mute/hold, конкурентные локальные и серверные завершения, replay после перезапуска Flutter, восстановление процесса и деградация хранилища.

### 15.3. Ручные уровни

Отдельная матрица фиксирует реальные APNs, FCM и Web Push, lock screen, DND, force-stop, особенности производителей и системный UI. Go server example — один из таких ручных стендов. Автоматические тесты не выдаются за device/provider validation.

## 16. GitHub Actions

GitHub Actions запускает независимые jobs на подходящих runners:

- Dart format, analyze, test и проверка 100% DartDoc публичного API;
- Android checks и example build;
- Apple checks и доступные iOS/macOS example builds;
- Windows checks и example build;
- Linux checks и example build;
- Web worker tests, JS и Wasm smoke;
- Go format, vet, test и build;
- согласованность fixtures и capability matrix;
- поиск случайно добавленных секретов.

CI не требует внешних Firebase/APNs credentials и не выполняет реальную provider-доставку. Такие проверки запускаются вручную и записываются в validation matrix.

## 17. Критерии первой стабильной версии

Первая стабильная версия готова, когда:

- все шесть платформ имеют зарегистрированный адаптер и честный capability report;
- входящие и исходящие звонки проходят заявленные платформенные сценарии;
- события переживают остановку Flutter в пределах задокументированных гарантий;
- автономная HTTPS-очередь восстанавливается после перезапуска;
- общий wire-format проверен contract fixtures;
- публичный Dart API документирован на 100%;
- GitHub Actions проходит на всех поддерживаемых runners;
- Go server example собирается и проходит собственные тесты, не являясь зависимостью библиотеки;
- validation matrix отделяет автоматические доказательства от реальных device/provider проверок.

## 18. Не входит в первую версию

- встроенный WebRTC, LiveKit или другой медиатранспорт;
- серверный signaling framework;
- обязательная зависимость от Firebase в библиотеке;
- гарантия поведения, которое ОС или браузер не разрешает обеспечить;
- production backend на основе `server_example`;
- сокрытие платформенных различий ради формально одинакового результата.
